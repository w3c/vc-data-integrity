Abstract

This document describes a threat model for the Data Integrity specification. It identifies and analyzes security and privacy threats specific to ecosystems that use Data Integrity proofs (created using cryptosuites such as ECDSA, EdDSA, and BBS) to secure the authenticity and integrity of documents such as verifiable credentials.

1. Introduction

Threat modeling is a vital part of specification development. This document provides a threat model for the Data Integrity specification, which defines a mechanism for ensuring the authenticity and integrity of structured data documents. The mechanism uses cryptographic proofs that are created and verified through transformation, hashing, and proof serialization algorithms.

This threat model follows the methodology described in the W3C Threat Modeling Guide and classifies threats using the STRIDE taxonomy. Threats are grouped into five categories:

  • Target Threats are threats the specification was designed to address.
  • Implementation Threats are threats that implementers must handle; the specification leaves the choice of mitigation open.
  • Deployment Threats are threats that arise from how systems are configured and operated.
  • External Threats are real-world risks acknowledged as out of scope for this version of the specification.
  • Dependency Threats are threats inherited from technologies the specification depends upon.

1.1 Description

The Data Integrity specification defines a mechanism for protecting the authenticity and integrity of documents through cryptographic proofs. A signer takes an input document, transforms it into a canonical form, hashes the result, and signs the hash using private key material held in a security module, producing a signed document that carries one or more proofs. The signed document is transmitted to a holder, who stores it in holder storage until it is needed and later transmits it to a verifier. The verifier runs the verify process (re-transforming, re-hashing, and cryptographically checking each proof) to confirm that the document was created by the signer and has not been modified since.

The core property the specification provides is that a verifier receiving a signed document can determine, in an automated and cryptographically verifiable way, whether the information in the document is authentic. This holds even when the document arrives long after it was created, over untrusted networks, and through intermediaries such as holders, and it requires no contact with the signer. The concrete cryptographic mechanisms are supplied by cryptosuites, such as those defined in the ECDSA, EdDSA, and BBS cryptosuite specifications, which instantiate the transformation, hashing, proof serialization, and proof verification algorithms that this threat model examines.

For this threat model, we consider a minimal instantiation of a Data Integrity ecosystem consisting of three roles: the Signer (E1) who creates signed documents, the Holder (E2) who stores them and transmits them to other parties, and the Verifier (E3) who checks their proofs and decides whether to accept them. In verifiable credential ecosystems, these roles correspond to the issuer, holder, and verifier.

Note

Note: We do NOT model potential attackers as first-class elements, as over-characterizing attackers can lead to analysis bias that is better avoided.

1.2 Data Flow Diagram for the Data Integrity Ecosystem

The data flow diagram below illustrates the key elements and data flows in a minimal Data Integrity ecosystem. The diagram shows how an input document (O1) is transformed, hashed, and signed within the signing system (C1) using key material held in the security module (S1), producing a signed document (O2) that is transmitted to the holder (E2), stored in holder storage (S2), and later transmitted to a verifier (E3), whose verify process confirms its authenticity.

The following notation is used in the diagram description and dictionary:

  • E denotes an External Entity (a human or legal person outside the system boundary)
  • P denotes a Process (a running algorithm that transforms data)
  • F denotes a Data Flow (movement of data between elements)
  • S denotes a Data Store (persistent or ephemeral storage)
  • O denotes a Data Object (a self-contained, transferable artifact)
  • C denotes a Contained System Boundary (a collection of elements under a single authority)

1.3 Dictionary

E1 Signer An entity (such as a credential issuer, a notary, a supply-chain participant, or an automated service) that makes cryptographically verifiable statements by creating Data Integrity proofs over input documents. The signer controls a controller document, such as a CID or a DID document, that expresses its verification methods, and controls the private key material corresponding to those verification methods. In verifiable credential ecosystems, this role is typically played by the issuer.
E2 Holder A person or organization that receives signed documents from a signer, stores them, and transmits them to verifiers. The holder typically operates a software application, such as a digital wallet, and controls when, to whom, and (when a selective disclosure cryptosuite is used) how much of a signed document is disclosed.
E3 Verifier An entity that receives a signed document and must determine whether the information it contains is authentic, meaning that it was created by the claimed signer and has not been modified since. The verifier runs the Verify process and accepts or rejects the document based on the result and on its own policy, such as which cryptosuites and proof purposes it accepts.
P1 Transform The process that converts an input document into the canonical form that is protected by a proof, using the transformation algorithm identified by the cryptosuite, for example, RDF Dataset Canonicalization (RDFC-1.0) or the JSON Canonicalization Scheme (JCS). Transformation ensures that the proof protects the information expressed by the document rather than one particular byte serialization of it. This process runs during both proof creation and proof verification.
P2 Hash The process that applies the cryptographic hash function identified by the cryptosuite to the transformed data, producing the compact value over which the proof is computed. This process runs during both proof creation and proof verification.
P3 Sign The process (called proof serialization by the specification) by which a signer produces a proofValue over the hashed data using private key material held in the Security Module, and assembles the complete proof, including its type, cryptosuite, verificationMethod, and proofPurpose properties and optional properties such as created, expires, domain, and challenge.
P4 Store The process by which a holder places a received signed document into Holder Storage and retrieves it later for transmission to a verifier.
P5 Verify The process by which a verifier checks a received signed document. It re-runs the cryptosuite's transformation and hashing over the document, cryptographically verifies the proofValue using the verification method referenced by the proof, and confirms that the verification method is bound to its controller and expressed under the verification relationship matching the proof's proofPurpose, that any expected domain and challenge values match, and that the document's contexts match known-good values.
F1 Transmit to Holder The data flow by which a signed document travels from the signing system to the holder system. This flow crosses the trust boundary between the signer's authority and the holder's authority.
F2 Transmit to Verifier The data flow by which a holder delivers a signed document to the verifier system. This flow crosses the trust boundary between the holder's authority and the verifier's authority, and is typically the first point at which the document is exposed to a party whose interests differ from the holder's.
S1 Security Module The protected key store within the signing system (such as a hardware security module, a trusted platform module, or an operating-system keystore) that holds the signer's private keys and performs signing operations without releasing private key material to application code.
S2 Holder Storage The persistent storage within the holder system where signed documents are kept, typically the storage of a digital wallet application. This storage is accessible only to the holder's software within the holder system boundary.
O1 Input Document A document, expressed in a syntax such as JSON or JSON-LD, that contains the information to be protected but does not yet carry a proof. It is the input to the proof-creation pipeline that runs within the signing system.
O2 Signed Document An input document combined with one or more Data Integrity proofs. A signed document can carry multiple proofs, either as a proof set (independent proofs over the same data, enabling cryptographic layering) or as a proof chain, where later proofs also protect earlier ones. It is self-contained: it can be transmitted and stored without losing its integrity protection.
C1 Signing System The system boundary, typically a server or service operated by or for the signer, within which the Transform, Hash, and Sign processes run and the Security Module resides. Everything inside this boundary is under the signer's authority.
C2 Holder System The system boundary, typically a mobile or desktop digital wallet application, within which the Store process runs and Holder Storage resides. Everything inside this boundary is under the holder's control.
C3 Verifier System The system boundary, typically an automated verification service, within which the Verify process runs. It is configured with the trust and policy decisions of the verifier, such as the cryptosuites, proof purposes, and document contexts it accepts.

2. Stakeholders

2.1 E1 Signer

A signer is an entity that creates Data Integrity proofs over documents. Signers range from credential issuers (universities, government agencies, employers) to notaries, supply-chain participants, and automated services that make cryptographically verifiable statements. In verifiable credential ecosystems, the signer is most often the issuer of a credential.

The signer's primary goals are that only documents it intends to sign carry its proofs, that its private key material remains under its exclusive control, and that the documents it signs remain verifiable by the parties intended to rely on them. A signer whose keys are compromised, or whose proofs can be forged, suffers direct reputational, financial, and legal harm.

2.2 E2 Holder

A holder is a person or organization that receives signed documents and transmits them to verifiers. In credential ecosystems, the holder is typically the subject of the credential (a student holding a diploma or an employee holding a professional certification) and stores signed documents in a digital wallet.

The holder's primary goal is that the documents they present are accepted by verifiers. Holders also have a strong interest in privacy: they do not want the act of presenting documents to enable signers, verifiers, or third parties to track their activities across contexts, and they want to disclose no more information than each interaction requires.

2.3 E3 Verifier

A verifier is an entity that receives signed documents and must decide whether to rely on them. Verifiers range from automated services processing high volumes of documents (customs systems, age-verification services, hiring platforms) to individuals checking a single document.

The verifier's primary goal is to accept only documents that are authentic: created by the claimed signer, unmodified since signing, and used for the purpose and in the context the signer intended. Verifiers also have a strong interest in availability: verification must complete within their operational time budgets even when processing untrusted, and potentially malicious, input.

3.2 Threat Details

Target Threats

3.2.1 T1. Signed Document Tampering

T1. Signed Document Tampering security

[Threat List]
An attacker with access to a signed document (while it is transmitted to a holder, kept at rest in holder storage, or transmitted to a verifier) modifies its contents to alter the claims it expresses. For example, an attacker might change the subject of a university degree credential, alter the amount on a signed invoice, or insert statements that the signer never made. A related variant strips the proof from a signed document entirely, or removes individual proofs from a proof set, in the hope that a downstream system will process the document without noticing the missing protection. Detecting modification of signed information, wherever it occurs in the document's lifecycle, is the central capability that the Data Integrity specification was designed to provide.
R1. Cryptographic Proof Verification (Reduce)
The verify process re-executes the cryptosuite's transformation and hashing over the received signed document and cryptographically verifies the proofValue against the signer's public key, so any modification of the protected information causes verification to fail. Verification detects tampering rather than preventing it, and residual risks remain: an incorrect canonicalization algorithm could allow two semantically different documents to produce the same canonical form, some signature schemes allow new proofs to be created over already-signed messages (for example, ECDSA is not strongly unforgeable), and some signature libraries omit required verification checks. Proof stripping is not detectable by cryptographic means; verifiers reject documents that do not carry the proofs their policy requires.
R2. Transformation Binds Proofs to Information Content (Reduce)
Cryptosuites transform the document into a canonical form before hashing and signing, binding the proof to the information content of the document rather than to one specific byte serialization. Benign changes such as whitespace, property ordering, or re-serialization between compatible syntaxes do not invalidate the proof, while any change to the meaning of the protected statements does. This narrows the tampering surface to semantic changes, which are exactly the changes that the verify process is designed to detect.
Affected Components: O2: Signed Document, F1: Transmit to Holder, F2: Transmit to Verifier, S2: Holder Storage, P4: Store, P5: Verify, C2: Holder System
Threat Taxonomy: STRIDE (Tampering)

Implementation Threats

3.2.2 T2. Canonicalization Resource Exhaustion

T2. Canonicalization Resource Exhaustion security

[Threat List]
Cryptosuites based on RDF Dataset Canonicalization transform documents through a canonical labeling algorithm whose worst-case behavior, for maliciously crafted inputs, requires excessive computation, a class of inputs known as poisoned datasets. An attacker submits such a crafted signed document to a verifier system, whose verify process must canonicalize the untrusted input before any proof can be checked, consuming processor time and memory and denying service to legitimate requests. Signing services are exposed in the same way when they run the transform process over an input document supplied by a third party. The Data Integrity specification requires that this class of attack be mitigated, but leaves the selection and configuration of mitigations (detection heuristics, resource limits, timeouts) to implementers.
R3. Poisoned Dataset Detection (Reduce)
Conforming RDF Dataset Canonicalization implementations are required to detect potentially poisoned datasets and abort processing rather than attempt to canonicalize them, and the canonicalization test suite exercises this behavior. Implementers confirm that the canonicalization library they deploy enforces these protections, since bounded work is still consumed before detection triggers and detection heuristics are necessarily imperfect.
R4. Resource Limits and Timeouts (Reduce)
Implementations bound the processing applied to any single document (input size limits, canonicalization timeouts, memory ceilings, and rate limiting on document intake) so that a single malicious signed document cannot exhaust the resources of the verifier system. These are the same classes of defense applied to any other untrusted input processed on the Web.
R5. JCS-Based Cryptosuite Selection (Eliminate)
For deployments that do not require RDF semantics, selecting a cryptosuite based on the JSON Canonicalization Scheme (such as eddsa-jcs-2022 or ecdsa-jcs-2019) eliminates this specific attack vector, because JCS canonicalization runs in time proportional to the size of its input. The trade-off is the loss of protections that RDF-based canonicalization provides, such as proofs that survive re-serialization of the document into other compatible syntaxes.
Affected Components: P1: Transform, P5: Verify, O1: Input Document, O2: Signed Document, C3: Verifier System
Threat Taxonomy: STRIDE (Denial of Service)

Deployment Threats

3.2.3 T3. Signing Key Compromise via Inadequate Key Protection

T3. Signing Key Compromise via Inadequate Key Protection security

[Threat List]
A signing system is deployed with its private signing keys inadequately protected: key material is stored in application memory or on disk instead of in a security module, keys remain in service far beyond recommended cryptoperiods, or a single key is reused across unrelated purposes such as both credential issuance and authentication. An attacker who obtains the key material can run the sign process at will, producing proofs that are indistinguishable from those created by the legitimate signer. The root event is a disclosure of the contents of the security module; the realized harm is the attacker spoofing the signer's signing authority. Every document that a verifier checks against the compromised key is affected until the compromise is discovered and the key is rotated.
R6. Security Module Key Storage (Reduce)
Deployments generate and store signing keys inside a dedicated security module (such as a hardware security module, a trusted platform module, or an operating-system keystore) that performs the sign operation internally and never releases private key material to application code. This substantially raises the cost of key exfiltration, although it does not prevent an attacker who controls the signing system from misusing the module to sign attacker-chosen documents while that access persists.
R7. Cryptoperiods and Key Rotation (Reduce)
Deployments bound the lifetime of signing keys following key-management guidance such as NIST SP 800-57, which recommends cryptoperiods of one to three years for signing keys, and rotate keys on schedule and immediately upon suspicion of compromise. Bounded cryptoperiods limit the window during which a compromised key can produce proofs that verifiers trust.
R8. Verification Relationship and Proof Purpose Validation (Reduce)
The Data Integrity specification requires that a verification method be expressed under the verification relationship that matches a proof's declared proofPurpose, and that the verify process confirm both the binding between the verification method and its controller and the match between the proof's purpose and the purpose the verifier expects. Keys deployed for a single purpose therefore cannot be silently repurposed for another, which contains the blast radius of any single key compromise.
Affected Components: S1: Security Module, C1: Signing System, P3: Sign, E1: Signer, P5: Verify
Threat Taxonomy: STRIDE (Spoofing)

External Threats

3.2.4 T4. Cross-Context Correlation via Proof Artifacts

T4. Cross-Context Correlation via Proof Artifacts privacy

[Threat List]
Two or more verifiers (or a signer colluding with a verifier) compare the signed documents each has received and correlate them using the cryptographic artifacts those documents carry. Even when a holder discloses only minimal document content, a static proofValue is effectively a globally unique identifier for the document, and the verificationMethod, created timestamp, and other proof metadata narrow the correlation further. Colluding parties can thereby link a holder's activities across unrelated contexts, building interaction profiles the holder never consented to, and a signer can discover where and when the documents it signed are being used. The collusion itself takes place entirely outside the systems this specification defines, so no specification text can prevent it; the specification can only reduce what the proof artifacts reveal.
R9. Unlinkable Derived Proofs (Reduce)
Cryptosuites that support unlinkable derived proofs, such as bbs-2023, allow a holder to present, for each transmission to a verifier, a freshly derived proof that is cryptographically unlinkable both to the original signature and to other derived proofs from the same signed document. Residual correlation signals remain even then: the total number of signed statements, the pattern of which statement indexes are revealed, and any globally unique @id values in the disclosed content can still narrow the anonymity set, and the BBS signature scheme is not post-quantum secure.
R10. Single-Use Documents (Reduce)
Signers issue batches of single-use signed documents so that each presentation to a verifier carries a distinct proofValue, leaving colluding parties nothing stable to join on at the proof layer. This shifts cost onto issuance volume and does not address correlation through the disclosed document content itself.
R11. Herd Privacy Practices (Reduce)
Signers keep the correlatable surface of the documents they sign small and common to many holders: verification methods shared across large populations, created timestamps that are coarse-grained or omitted, and no per-document identifiers in proof metadata. Any individual signed document is then indistinguishable from those of a large herd of holders, and correlation yields little.
R12. Accept Where Linkability Is Required (Accept)
Some ecosystems require strong correlation by design (regulated audit trails, anti-money-laundering obligations, or the tracking of hazardous materials), and in those settings linkable proofs are the intended behavior rather than a defect. Deployments in such ecosystems accept this threat for the flows where linkability is mandated and disclose that acceptance to their participants.
Affected Components: E1: Signer, E2: Holder, E3: Verifier, O2: Signed Document, F2: Transmit to Verifier
Threat Taxonomy: STRIDE (Information Disclosure)

Dependency Threats

3.2.5 T5. Cryptographically Relevant Quantum Computer Breaks Signature Suites

T5. Cryptographically Relevant Quantum Computer Breaks Signature Suites security

[Threat List]
Every currently registered Data Integrity cryptosuite (ECDSA over the P-256 and P-384 curves, EdDSA over Ed25519, and BBS over BLS12-381) inherits its security from the hardness of elliptic-curve discrete logarithms. A cryptographically relevant quantum computer (CRQC) running Shor's algorithm would recover private keys from public keys, allowing an attacker to perform the sign process for any signer whose public key it has observed and to forge signed documents that verify as authentic. This collapses the mitigation on which the tamper-detection guarantee of this specification rests (see T1), and it applies retroactively: documents signed before migration become forgeable the moment the capability exists, even though the hash functions used by the hash process are not practically broken by known quantum algorithms.
R13. Cryptographic Agility (Reduce)
The cryptosuite architecture separates the proof from the document it protects and identifies the suite in every proof, so deployments that remain connected can migrate to a post-quantum signature suite through a configuration change once one is standardized. Post-quantum Data Integrity cryptosuites based on NIST-standardized algorithms, such as ML-DSA, are under active incubation. Agility enables migration for newly created proofs; it does nothing for documents that cannot be re-issued.
R14. Cryptographic Layering via Proof Sets (Reduce)
Because a signed document can carry a proof set, signers of long-lived documents layer proofs from independent cryptosuites (for example, a classical suite alongside a post-quantum suite during the migration period) so that the compromise of one algorithm family leaves the other proof intact. The residual risk is retroactive forgery: proofs created before layering or migration become forgeable once a CRQC exists, and only re-issuance of those documents, together with verifier-side deprecation of broken suites, addresses the legacy population.
R15. Date-Versioned Cryptosuite Names (Reduce)
Cryptosuite identifiers embed their year of design (eddsa-rdfc-2022, ecdsa-rdfc-2019, bbs-2023), giving developers and auditors an immediate, human-readable signal of cryptographic age. Aging identifiers prompt the periodic review, upgrade, and deprecation decisions on which timely migration away from broken algorithms depends.
Affected Components: P3: Sign, P5: Verify, O2: Signed Document, E1: Signer
Threat Taxonomy: STRIDE (Tampering)

4. Contributing

This threat model is maintained alongside the Data Integrity specification. Feedback, bug reports, and proposed additions are welcome via the issue tracker.

4.1 Adding a Threat

To add a new threat to the model, provide the following components:

  1. A short, descriptive name
  2. A unique ID (letter T followed by an integer, e.g., T6)
  3. A description of the threat with enough detail for readers to understand its scope
  4. One or more responses, each with a name, unique ID (letter R followed by an integer), response type (Eliminate, Reduce, Transfer, or Accept), and description
  5. A list of affected DFD elements drawn from the dictionary above
  6. The threat taxonomy used (e.g., STRIDE) and the threat class within that taxonomy

Create a YAML file following the pattern of the existing threat files in the threats/ directory, then register it in threats/outline.yaml by adding its filename to the files list and its threat ID to the appropriate category in the categories list. No changes to index.html are required.
